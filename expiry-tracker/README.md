# تتبع تواريخ الصلاحية

نظام يعرف تواريخ انتهاء صلاحية بضاعة المحل وينبّه صاحبه قبل وقت كافٍ ليتصرف.
تطبيق ويب (PWA) عربي RTL يعمل من متصفح الموبايل، وقاعدته Supabase.

**الوحدة الأساسية في النظام هي الوجبة (batch) وليست المنتج** — المنتج الواحد قد
تكون له عدة وجبات بتواريخ مختلفة على الرف بنفس الوقت.

## التشغيل

```bash
git clone https://github.com/husainhakam089-rgb/simulators.git
cd simulators/expiry-tracker
npm install
cp .env.example .env       # جاهز بمفاتيح المشروع
npm run dev                # http://localhost:5173
```

`npm install` ينسخ ملفات محرك القراءة إلى `public/ocr` تلقائياً، وكذلك
`npm run dev` و`npm run build` قبل تشغيلهما. لتكرارها يدوياً: `npm run ocr:assets`.

### على الموبايل

الكاميرا وWeb Push لا يعملان إلا على **HTTPS** (أو `localhost` على نفس الجهاز):

```bash
npm run build              # ينتج مجلد dist
```

ارفع `dist` على أي استضافة ثابتة تدعم HTTPS (Netlify أو Vercel أو Cloudflare
Pages). **اضبط إعادة توجيه كل المسارات إلى `index.html`** لأنه تطبيق صفحة واحدة:

- Netlify — ملف `dist/_redirects` فيه سطر واحد: `/*  /index.html  200`
- Vercel — `vercel.json`: `{ "rewrites": [{ "source": "/(.*)", "destination": "/index.html" }] }`

ثم افتح الرابط بالموبايل و«أضِف إلى الشاشة الرئيسية» ليعمل كتطبيق ويصله الإشعار.

### أول مرة داخل التطبيق

1. **تسجيل محل جديد** — اسم المحل واسمك ورقم هاتفك ورمز من ٦ أرقام. تُنشأ معه
   ٢٠ مجموعة جاهزة بأعمارها.
2. **استيراد الأصناف** — صدّر ملف الأصناف من نظام المبيعات وارفعه؛ راجع مطابقة
   الأعمدة مرة واحدة فقط.
3. **أعمار المجموعات** — راجع العمر الافتراضي ومتى يبدأ التنبيه لكل مجموعة.
4. **الطاقم** — أضف العمال. كل عامل يدخل برقم هاتفه ورمزه ولا يرى إلا الكاميرا.
5. **الإشعارات** — من اللوحة، «فعّل الإشعارات» ثم «إشعار تجريبي» للتأكد.

بعدها يبدأ العمال بالتصوير، ويصلك ملخص واحد كل صباح الساعة ٦ بتوقيت بغداد.

## قاعدة البيانات

المهاجرات في `supabase/migrations/` بالترتيب، والدوال الطرفية في
`supabase/functions/`. لمشروع جديد:

```bash
supabase link --project-ref <ref>
supabase db push
supabase functions deploy signup-store --no-verify-jwt
supabase functions deploy admin-create-worker
supabase functions deploy send-digest-push --no-verify-jwt
```

ثم ولّد مفاتيح VAPID مرة واحدة واحفظها في `private.app_secrets`
(انظر التعليق أسفل `0006_secrets_and_grants.sql`)، وحدّث `functions_url`
في `0005_cron.sql` إن تغيّر عنوان المشروع.

### الجداول

`stores` · `users` · `categories` · `products` · `batches` · `alerts` ·
`actions_log` · `import_mappings` · `push_subscriptions` · `daily_digests`

### الدوال المهمة

| الدالة | الغرض |
|---|---|
| `worker_lookup(barcode)` | بحث العامل عن صنف — **لا تُرجع أي سعر** |
| `worker_catalog()` | كتالوج مختصر يُخزَّن محلياً ليعمل البحث دون اتصال |
| `record_batch(...)` | تسجيل وجبة، idempotent عبر `client_id` لتفادي التكرار بالمزامنة |
| `import_products(jsonb)` | استيراد/تحديث الأصناف دفعة واحدة (للأدمن) |
| `run_daily_alerts()` | محرك التنبيهات — يعمل يومياً بـ pg_cron |
| `dashboard_summary()` | قيمة البضاعة المعرّضة خلال ٧ / ٣٠ / ٩٠ يوم |
| `compliance_report(days)` | من صوّر ومن لم يصوّر |
| `record_action(...)` | تنزيل سعر / إرجاع / نقل / إتلاف |

## الأدوار والصلاحيات

- **العامل** لا يرى إلا الكاميرا. أسعار الكلفة محجوبة عنه **على مستوى قاعدة
  البيانات** لا على مستوى الواجهة: سياسة RLS تمنع قراءة جدول `products` عن
  غير الأدمن، والعامل يصل للأصناف عبر `worker_lookup` و`worker_catalog`
  اللتين لا تُرجعان أي حقل سعر.
- **الأدمن** يرى كل شيء داخل محلّه فقط. كل جدول محصور بـ `store_id`.
- الدخول برقم الهاتف ورمز من ٦ أرقام. الرقم يُحوَّل داخلياً إلى بريد
  `<digits>@expiry.local` لأن Supabase Auth يطلب بريداً — لا يُرسل بريد أبداً،
  والحسابات تُنشأ من دوال طرفية بمفتاح الخدمة (`email_confirm: true`).

## التنبيهات

1. `pg_cron` يشغّل `run_daily_alerts()` الساعة ٠٣:٠٠ UTC = **٠٦:٠٠ بغداد**،
   قبل فتح المحل وخارج فترة الصمت (٩ مساءً – ٦ صباحاً).
2. المحرك يحسب الأيام المتبقية لكل وجبة نشطة، ويقارنها بـ `alert_before_days`
   الخاص بمجموعتها، ويحسب **قيمة الخسارة المتوقعة = الكمية × سعر الكلفة**.
3. يكتب **ملخصاً واحداً** في `daily_digests` («١٨ صنفاً يحتاج انتباهك — قيمتها
   ٢٫٤ مليون دينار»)، ثم تُرسله دالة `send-digest-push` عبر Web Push.
4. القائمة في التطبيق **مرتبة حسب المبلغ لا حسب التاريخ**، وكل سطر يحمل أزرار
   القرار مباشرة.

إشعار واحد باليوم كحد أقصى — لا إشعار لكل منتج. تنفيذ Web Push مكتوب يدوياً
فوق WebCrypto (RFC 8291 aes128gcm + RFC 8292 VAPID) في
`supabase/functions/send-digest-push/webpush.ts`، بلا أي مكتبة خارجية.

## قراءة التاريخ من الصورة

القراءة تجري **داخل الموبايل نفسه** (Tesseract فوق WebAssembly)، لا على خادم:
تعمل بلا إنترنت، بلا كلفة لكل صورة، ولا تغادر صورة الكارتون الجهاز.

### كيف تسير

1. الكاميرا تمسك الباركود ← تُلتقط صورة الكارتون ← تظهر شاشة التأكيد **فوراً**
   بالتاريخ المحسوب من عمر المجموعة.
2. القراءة تعمل بالخلفية (٣٠٠–٩٠٠ مللي ثانية على جهاز متوسط). إن وجدت تاريخاً،
   حدّثت شاشة التأكيد وكُتب عليها «قُرئ من صورة الكارتون».
3. **لا تنتظر القراءة أبداً**: زر التأكيد شغّال طوال الوقت، وإن ضغط العامل قبل
   انتهائها حُفظ التاريخ المعروض. وإن عدّل التاريخ بيده فالقراءة لا تلمسه.
4. المحرك يُحمَّل مسبقاً عند فتح شاشة العامل، فيكون جاهزاً قبل أول كارتون.

### الصيغ المدعومة

`18/09/2027` · `18.09.27` · `2027-09-18` · `09/18/2027` (أمريكي، يُكتشف تلقائياً) ·
`09/2027` و`09/27` (شهر/سنة ← آخر يوم في الشهر) · `18 SEP 2027` · `SEP 2027` ·
`EXP 18092027` (مضغوط) · والأرقام العربية `١٨/٠٩/٢٠٢٧`.

الكلمة المفتاحية ليست شرطاً: تاريخ مطبوع وحده يُقرأ. وهي فقط ترفع الثقة وتحسم
الالتباس حين يكون على الكارتون أكثر من تاريخ.

**الصيغة القصيرة `09/27`** تُقبل بلا كلمة مفتاحية بشرطين: أن تكون في المستقبل
وضمن خمس سنوات. خارج هذه النافذة تحتاج كلمة صريحة، لأنها تشبه أرقام التشغيلة
تماماً — و`12/25` وحده يُرفض بينما `EXP 12/25` يُقبل.

### الإنتاج أم الانتهاء؟

بهذا الترتيب:

1. **كلمة مفتاحية صريحة** — `EXP` / `BEST BEFORE` / `USE BY` / «تاريخ الانتهاء»
   مقابل `MFG` / `PROD` / `PKD` / «تاريخ الإنتاج». أعلى ثقة.
2. **تاريخان بلا كلمات** ← الأبعد هو الانتهاء والأقرب هو الإنتاج.
3. **تاريخ واحد في المستقبل** ← انتهاء.
4. **تاريخ واحد في الماضي** ← يُعامَل كإنتاج ويُضاف عمر المجموعة، أو كصنف منتهٍ
   إن لم يكن للمجموعة عمر. الحالتان تُحفظان بثقة منخفضة ويراجعهما المدير.

كل وجبة تحفظ `date_source` (`ocr` / `calculated` / `manual`) و`confidence`
وسبب اختيار التاريخ نصّاً، وكلها تظهر للمدير في شاشة المراجعة مع صورة الكارتون.

### حدود القراءة

- **إنجليزي فقط.** الكلمات العربية على الكارتون لا تُقرأ (إضافة النموذج العربي
  تعني ميغابايتات أخرى ودقة أقل على الطباعة الصناعية). الأرقام العربية تُقرأ
  وتُحوَّل، والتواريخ نفسها تكاد تكون دائماً بأرقام لاتينية.
- **الطباعة الباهتة جداً على خلفية مزخرفة لا تُقرأ.** هذا مقصود ومُختبَر: المحرك
  يرجع فارغاً بدل أن يخترع تاريخاً، فيبقى التاريخ المحسوب. تاريخ مخترع يعني
  بضاعة سليمة تُتلف، أو بضاعة خربانة تُباع.
- **الأرقام المتجاورة قد تُلتبس.** رقم تشغيلة مثل `L 09/27` سيُقرأ تاريخاً. هذا
  ثمن قبول الصيغة القصيرة، ويظهر للمدير في شاشة المراجعة مع صورة الكارتون.
- **حجم التحميل الأول ~٧ م.ب** (المحرك + النموذج اللغوي). يُحمَّل مرة واحدة لكل
  جهاز ويُخزَّن دائماً في عامل الخدمة، ثم يعمل دون إنترنت. التطبيق يشتغل كاملاً
  قبل تحميله ومن دونه — القراءة تحسين لا شرط.
- ملفات المحرك تُنسخ من `node_modules` إلى `public/ocr` عند البناء
  (`npm run ocr:assets`) ولا تُحفظ في المستودع.

## العمل دون اتصال

التسجيل لا ينتظر الإنترنت أبداً:

- الكتالوج (باركود ← اسم وعمر افتراضي، **بلا أسعار**) مخزون في IndexedDB.
- كل وجبة تُحفظ محلياً مع صورة الكارتون، ويظهر التأكيد فوراً.
- المزامنة تعمل عند عودة الاتصال وكل ٣٠ ثانية، و`client_id` يمنع التكرار
  مهما تكررت المحاولات.

|---|---|
